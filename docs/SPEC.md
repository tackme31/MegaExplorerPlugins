# WD Tagger プラグイン 仕様

> **状態（2026-10-02）**: 機能はほぼ確定。§1 が決定事項、§2 が MEGA 側の制約、§3 が処理の流れ、
> §4 が決定の根拠になった実測、§5 が未決事項、§6 がこのプラグインを作るのに MegaExplorer 側の
> プラグイン基盤で足りないもの。未決が決まったら §1 に移す。

WD14 系のタグ付けモデル（ONNX）で MEGA 上の画像・動画を推論し、結果を MEGA のノードタグとして
付けるプラグイン。推論部分は以前作ったローカル用タグ付けツール（`ImagePreprocessor` / `TagModel`）を
移植する。

## 1. 決定事項

### コマンドと対象

- コンテキストメニューに 2 コマンド（表示は英語）
  - ファイルを右クリック: **Tag this item**
  - フォルダを右クリック: **Tag everything in this folder**（配下を再帰的に）
- 対象は画像と動画。判定は 2 段階
  1. **拡張子**で絞る（旧ツールのリスト: `.png .jpg .jpeg .webp .bmp` と
     `.mp4 .avi .mkv .webm .mov .wmv .flv .m4v .gif`）
  2. 処理中に **`items.fetchPreview` でプレビューが取れなかったらスキップ**
- 動画もプレビュー（MEGA が持つ代表フレームの JPEG）で推論する。動画をダウンロードしてフレームを抜く、
  ということはしない
- **推論タグ（`wd:` タグ）がすでにあるアイテムはスキップする**

### タグの書式

- **タグはカテゴリごとに分けて付ける**。カテゴリ名をプレフィックスにし、検索で絞り込めるようにする
  - general: 全部を **1 つのタグに空白区切りでまとめる**。例: `wd:1girl long_hair smile`。
    MEGA のタグは 1 アイテム 10 個までなので（§2）、1 個に収める。検索は部分一致なので、
    タグを分けても 1 つにまとめても検索性はほぼ変わらない（§2）
  - rating: 1 個。例: `rating:general`（値は `general`/`sensitive`/`questionable`/`explicit` の 4 つ。
    Danbooru の旧 `safe` はない）
  - character: 1 キャラにつき 1 個。例: `character:hatsune_miku`。最大 3 個で、超えたらスコア上位の 3 個
  - 合計で最大 5 枠になり、ユーザー用に 5 枠が残る
- 区切り文字は**空白**。モデルの 10,861 タグに空白は 1 つも含まれていない。Danbooru 自身もタグ列を
  空白区切りで扱う。`;` `|` `/` `:` `\` `?` は顔文字タグ（`;d`、`:|`、`\m/` など）に含まれるので使えない
- タグの表記は WD の生のまま（`long_hair`、`hatsune_miku_(vocaloid)`）。`_` は空白に置き換えない
- `wd:` / `rating:` / `character:` で始まるタグはプラグインのものとして扱う。ユーザーが手で同じ
  プレフィックスのタグを付けていても区別しない
- 公式クライアントでは長いタグが 1 個並ぶ見た目になる。これは受け入れる
- 検索は部分一致なので、`general` とだけ検索すると `rating:general` にも当たる。これは仕方ないものとして
  受け入れる。絞り込むときは `rating:general` のようにプレフィックスまで含めて検索する

### 件数と閾値

- 件数は固定しない。**閾値で選ぶ**。既定値は旧ツールと同じ general 0.30 / character 0.50 / rating 0.40
- 推論タグ全体は最大 2000 バイト程度に抑える（超えたらスコアの低いものから落とす）。書き込む前に、
  既存のユーザータグとの合計が 3000 バイト以内かを確認する（根拠は §4）

### エラー

- GPU（CUDA）が使えないときは CPU で動かさない。**エラーを出して終える**（今はトースト。ダイアログの
  API ができたらそちら）
- アイテム単位のエラー（プレビュー取得や更新の失敗）では止めず、数えて最後にまとめて報告する

## 2. 前提となる MEGA 側の制約（SDK v10.17.0 で確認）

| 制約 | 値 | 出典 |
| --- | --- | --- |
| 1 ノードあたりのタグ数 | **最大 10**（超えると `API_ETOOMANY`） | `MegaClient::MAX_NUMBER_TAGS` |
| タグ全体の長さ | `,` 区切りで連結して **3000 バイト以内** | `MegaClient::MAX_TAGS_SIZE` |
| 使えない文字 | `,`（区切り文字） | `megaapi.h` `addNodeTag` |
| 重複判定 | 大文字小文字・アクセントを無視 | `getTagPosition` |
| description の長さ | 3000 バイト以内 | `MAX_NODE_DESCRIPTION_SIZE` |

**10 個という上限は、ユーザーが手で付けたタグと共有になる。**WD のモデルは閾値 0.30 で平均 47 個の
general タグを出すので（§4）、推論結果をタグ 1 個ずつに分けて付けることはできない。§1 で 1 タグに
まとめることにしたのはこのため。

**タグ検索（`MegaSearchFilter::byTag`）は部分一致。**検索語の前後に `*` を付けたパターン（`TextPattern`）を、
タグ 1 個ずつと照合する（`NodeSearchFilter::isValidTagSequence`）。大文字小文字とアクセントは区別しない。
sqlite 経由の検索も同じ関数を呼ぶ。1 回の検索で指定できるタグ語は 1 つだけで、`,` を含めると結果は空になる。
`byDescription` も部分一致。したがってタグを分けても、`hair` で検索すれば `long_hair` に当たる。
1 タグにまとめて失うのは「`hair smile` のように 2 語にまたがる検索も当たってしまう」程度。

## 3. 処理の流れ

```
command "tag-item" / "tag-folder":
    targets = 選択アイテム                       # tag-folder なら配下を再帰列挙してファイルだけ
    targets = [t for t in targets if 拡張子が画像/動画]
    model = load_model()                          # CUDA が使えなければエラーで終了
    progress(0, len(targets))
    for item in targets:
        check_cancelled()
        if item に wd: タグがある: skipped += 1; continue     # タグは items.get で取る
        try:
            jpg = fetch_preview(item)
        except NoPreview: skipped += 1; continue
        scores = model.predict(jpg); delete jpg
        tags = select_tags(scores)                # 閾値、character 3 個、2000 バイト
        update(item, tags_add=tags)
        progress(i, len(targets))
    return "Tagged N, skipped M, failed K"
```

## 4. 決定の根拠: タグの長さの実測

モデル（wd-eva02-large-tagger-v3）の `selected_tags.csv` に載っている 10,861 タグの長さ（UTF-8 バイト）:

| カテゴリ | 平均 | 中央値 | 上位10% | 最大 | 出現頻度で重み付けした平均 |
| --- | --- | --- | --- | --- | --- |
| general | 11.8 | 11 | 18 | 44 | 9.5 |
| character | 17.3 | 16 | 26 | 66 | 16.4 |
| rating | 9.0 | — | — | 12 | — |

推論でよく出るのは出現頻度の高いタグで、区切り 1 文字を含めると 1 タグ 10〜13 バイトになる。
3000 バイトを丸ごと使えば 230〜270 個、2000 バイトでも約 150 個入る。

旧ツールの DB に保存してある 528,581 件の推論結果（同じモデル、閾値 0.30 / 0.50 / 0.40）を、
§1 の書式に当てはめて計算した結果:

| 項目 | 平均 | 中央値 | 上位10% | 上位1% | 最大 |
| --- | --- | --- | --- | --- | --- |
| general の個数 | 46.9 | 45 | 66 | 93 | 595 |
| character の個数 | 0.7 | 1 | 2 | 4 | 73 |
| `wd:` タグのバイト数 | 512 | 494 | 727 | 1,039 | 6,909 |
| プラグインのタグ合計のバイト数（`,` 区切り） | 549 | 532 | 771 | 1,085 | 7,031 |

`wd:` タグが 2000 バイトを超えたのは 48 件（0.01%）、合計が 3000 バイトを超えたのは 4 件だけだった。
最大値のような外れ値（ノイズのような画像と思われる）を除けば、**バイト数は事実上の制約にならない**。
character が 4 個以上の画像は 6,152 件（1.2%）で、上限 3 個でほぼ全件をカバーできる。

## 5. 未決事項

### 5-1. 大きいフォルダ（要検討）

- 数百〜数千件を想定する。進捗（`ui.progress`）とキャンセルは必須
- **MEGA の API 制限**: 1 件につき `fetchPreview`、`items.get`、タグの追加が 1〜3 回ずつ走る。数百件を
  続けて処理すると制限にかかる可能性がある。最悪の場合、数件ごとにインターバルを入れる。どこで
  制限にかかるかを実際に測ってから決める
- `fetchPreview` を 1 件ずつ待つと遅いかもしれない。先読み（パイプライン化）は、上の制限との
  兼ね合いも含めて計測してから決める

### 5-2. モデルと設定ファイル

- モデル: `SmilingWolf/wd-eva02-large-tagger-v3`（約 1.2 GB）。初回の実行で Hugging Face から取得する
  （開発機では旧ツールが取得したものが HF キャッシュにすでにある）。ダウンロード中も進捗を出す
  （不定の表示）
- 置き場所は HF のキャッシュ（`~/.cache/huggingface`）のままでよいか
- 設定（モデル・閾値）はプラグイン自身が持つ。アプリは場所を決めない（v1 の方針どおり）。
  プラグインフォルダの `config.json` を想定

### 5-3. 将来: 付け直しのコマンド

§1 で付与済みのアイテムはスキップすることにした。閾値やモデルを変えて付け直したくなったら、
`wd:` / `rating:` / `character:` のタグを消してから付け直すコマンドを別に足す。

## 6. プラグイン基盤（MegaExplorer 側）への宿題

このプラグインを作るのに今の基盤で足りないもの。直すのは本体リポジトリの `feature/plugin-v1` で行う。

| # | 内容 | 必須度 | 現状 |
| --- | --- | --- | --- |
| 6-1 | **ファイルとフォルダでメニューを出し分ける**（manifest の `when` など） | 必須（§1 の 2 コマンド） | 未実装。今は全コマンドがファイルにもフォルダにも出る |
| 6-2 | フォルダ配下の再帰列挙（`items.descendants`） | あれば楽 | 未実装。`items.children` を再帰で呼べば代わりになる |
| 6-3 | ItemRef / items.get に種別（`kind`）を載せる | 任意（今は拡張子で判定する） | なし |
| 6-4 | 結果の詳細表示とエラーダイアログ（スキップ・失敗の一覧、GPU が使えないときのエラー） | 任意 | トーストの 1 行だけ |
| 6-5 | タグの一致判定を SDK に合わせる（大文字小文字・アクセントを無視） | 推奨 | アプリの事前チェック（`PluginHostApi::itemsUpdate`）は完全一致で比べている。SDK と食い違うので、`Long_Hair` があるところへ `long_hair` を add すると SDK が `API_EEXIST` を返して -32010 になり、remove は「無い」と判断されて黙って何もしない |
| 6-6 | 10 個の上限に当たったときのエラーを、-32010 以外の分かる形で返すか | 要確認 | `API_ETOOMANY` は今 -32010（MegaError）として返る |
| 6-7 | items.update でタグの remove を add より先に実行する | 推奨（付け直しのコマンド §5-3 を作るなら必要） | 今の実行順は add → remove。タグが 10 個埋まっているアイテムで付け替えると、add の時点で `API_ETOOMANY` になり、何も消えないまま止まる |
| 6-8 | アプリの検索をタグ（と説明）にも広げる（`byTag`/`byDescription`） | 後回し（必要になってから） | 今の検索は `byName` だけなので、付けたタグはアプリから検索できない |
