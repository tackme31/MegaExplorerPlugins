# WD Tagger プラグイン 仕様

> **状態（2026-10-02）**: 機能は確定。Tag / Retag（選択・フォルダ）とも実装済み。プラグイン基盤の改善（§6-A）は 1〜5 とも済。§1 が決定事項、§2 が MEGA 側の制約、§3 が処理の流れ、
> §4 が決定の根拠になった実測、§5 が未決事項、§6 がこのプラグインを作るのに MegaExplorer 側の
> プラグイン基盤で足りないもの。未決が決まったら §1 に移す。

WD14 系のタグ付けモデル（ONNX）で MEGA 上の画像・動画を推論し、結果を MEGA のノードタグとして
付けるプラグイン。推論部分は以前作ったローカル用タグ付けツール（`ImagePreprocessor` / `TagModel`）を
移植する。

## 1. 決定事項

### コマンドと対象

- コンテキストメニュー（WD Tagger のサブメニュー）に 4 コマンド（表示は英語）
  - ファイルを右クリック: **Tag selected** / **Retag selected**
  - フォルダを右クリック: **Tag all in folder** / **Retag all in folder**（配下を再帰的に）
  - Tag は `wd:` タグがあるアイテムを飛ばす。Retag は全件を推論し直し、プラグインのタグ（`wd:` / `rating:` /
    `chara:`）を新しい結果に置き換える。`items.update` には古いプラグインのタグを全部 `remove`、新しいタグを
    全部 `add` に入れて渡すだけで、MEGA へは変わったタグだけをアプリが送る（§6-5）。結果が同じなら MEGA への
    通信は起きず、更新後のタグが元と同じアイテムは `unchanged` として数える
  - Retag は 2 つとも、推論を始める前に確認ダイアログ（`ui.confirm`、`danger`）を出す。対象が 1 件ならファイル名、
    複数なら件数を出す（フォルダは配下を列挙し終えてから聞くので件数が分かる）。キャンセルしたら何もせず、
    トーストも出さない。推論の途中でキャンセルすれば、未処理のアイテムは元のまま。処理中の 1 件は書き換えを
    終えてから止まる
- 対象は画像と動画。判定は 2 段階
  1. **拡張子**で絞る（旧ツールのリスト: `.png .jpg .jpeg .webp .bmp` と
     `.mp4 .avi .mkv .webm .mov .wmv .flv .m4v .gif`）
  2. 処理中に **`items.fetchPreview` でプレビューが取れなかったらスキップ**
- メニューの出し分けは manifest の `when.targets` で行う。Tag selected / Retag selected は `"targets": "files"`、
  Tag all in folder / Retag all in folder は `"targets": "folders"`。**`extensions` は書かない**: 書くと画像と PDF を
  混ぜて選んだときに項目ごと灰色になるので、押せるようにしておき、画像・動画以外はプラグイン側でスキップする
- 結果は全コマンドとも `"result": "dialog"`。進捗ダイアログがそのまま結果表示に変わり、閉じるまで残る。
  1 行目が要約（例: `Tagged 120, 8 without a preview, 2 failed`）、その下に失敗とプレビューなしの一覧（パス付き）
- 動画もプレビュー（MEGA が持つ代表フレームの JPEG）で推論する。動画をダウンロードしてフレームを抜く、
  ということはしない
- **推論タグ（`wd:` タグ）がすでにあるアイテムはスキップする**

### タグの書式

- **タグはカテゴリごとに分けて付ける**。カテゴリ名をプレフィックスにし、検索で絞り込めるようにする
  - general: 全部を **1 つのタグに空白区切りでまとめる**。例: `wd:1girl long_hair smile`。
    MEGA のタグは 1 アイテム 10 個までなので（§2）、1 個に収める。検索は部分一致なので、
    タグを分けても 1 つにまとめても検索性はほぼ変わらない（§2）
  - rating: 1 個。例: `rating:general`（値は `general`/`sensitive`/`questionable`/`explicit` の 4 つ。
    Danbooru の旧 `safe` はない）
  - character: しきい値を超えたキャラを、スコアの高い順に **1 つのタグに空白区切りでまとめる**。
    各キャラに `chara:` を付ける。例: `chara:hatsune_miku chara:mari_(blue_archive)`。
    1 個に収めるので人数の上限はない（しきい値は旧ツールと同じ 0.50）。`chara:hatsune_miku` で検索すれば
    そのキャラに当たる。プレフィックスは短さを優先して `chara:`（`character:` は長く、`char:` は
    プログラミングの型名に見える）
  - 合計で最大 3 枠になり、ユーザー用に 7 枠が残る
- 区切り文字は**空白**。モデルの 10,861 タグに空白は 1 つも含まれていない。Danbooru 自身もタグ列を
  空白区切りで扱う。`;` `|` `/` `:` `\` `?` は顔文字タグ（`;d`、`:|`、`\m/` など）に含まれるので使えない
- タグの表記は WD の生のまま（`long_hair`、`hatsune_miku_(vocaloid)`）。`_` は空白に置き換えない
- `wd:` / `rating:` / `chara:` で始まるタグはプラグインのものとして扱う。ユーザーが手で同じ
  プレフィックスのタグを付けていても区別しない
- 公式クライアントでは長いタグが 1 個並ぶ見た目になる。これは受け入れる
- 検索は部分一致なので、`general` とだけ検索すると `rating:general` にも当たる。これは仕方ないものとして
  受け入れる。絞り込むときは `rating:general` のようにプレフィックスまで含めて検索する

### 件数と閾値

- 件数は固定しない。**閾値で選ぶ**。既定値は旧ツールと同じ general 0.30 / character 0.50 / rating 0.40
- 推論タグ全体は最大 2000 バイト程度に抑える（超えたらスコアの低いものから落とす）。書き込む前に、
  既存のユーザータグとの合計が 3000 バイト以内かを確認する（根拠は §4）。収まらないときや 10 枠に
  足りないときは、スコアの低いキャラ → rating → スコアの低い general の順に落とす

### モデルと設定

- モデルは `SmilingWolf/wd-eva02-large-tagger-v3`（約 1.2 GB）。置き場所は **HF のキャッシュ**
  （`~/.cache/huggingface`）のまま。初回の実行で Hugging Face から取得する
- 進捗は 1 つのダイアログの中で段階が切り替わる（`ui.progress` は通知ごとに表示を置き換えるので、
  アプリ側の変更は要らない）
  1. モデルのダウンロード（キャッシュにあれば飛ばす）: `Downloading model (first run only)`、件数は **MB**
     （ダイアログは `current / total` を単位なしで出すため。単位の指定は §6-10）
  2. モデルの読み込み: `Loading model…`、`total` を省いて不定の表示
  3. タグ付け: `Tagging…`、件数はアイテム数
- ダウンロード中はキャンセルできない（終わるまで戻らない）。問題があれば後で別スレッド化する
- onnxruntime-gpu は **1.23.2 に固定**。1.24 以降は CUDA 13 向けのビルドで、CUDA 12 の環境では CUDA プロバイダを読めず黙って CPU になる
- 設定（モデル・閾値）は**プラグインフォルダの `config.json`**。アプリは場所を決めない（v1 の方針どおり）

### 大きいフォルダと MEGA への負荷

- Tag all in folder は `items.descendants`（`type: "file"`）で配下を全部列挙し（列挙中も進捗とキャンセルが効く）、
  集めたファイルを Tag と同じ処理に流す。選択したファイルも `items.descendants` の結果もタグを含むので、`items.get` は呼ばない
- 1 件ずつ順番に処理する（`fetchPreview` → 推論 → タグの追加）。先読みや並列化はしない
- **MEGA に対する負荷テストはしない。**数百〜数千件を続けて流して API 制限がどこでかかるかを測る、
  という検証は、MEGA のサービスに意図的に負荷をかけることになり倫理上よくないので行わない。
  動作確認はテストアカウントの少数のアイテム（`TaggingTest` 程度）だけで行う
- その代わり、負荷を増やす方向の最適化（先読み・並列化・インターバルなしでの高速化）は入れない。
  実際の利用で制限エラーが出たら、そのとき件数ごとのインターバルや待ち直しを検討する
- **同時に動かすのは 1 つだけ。**MegaExplorer は多重起動でき、窓ごとに別のプラグインプロセスが立つ。タグの更新は MEGA 側でタグ一覧を丸ごと書き換えるので、同じファイルを同時に処理すると互いの変更を上書きしうる。全コマンドが最初に名前付きミューテックス（`Local\com.takumi.wdtagger.run`、`single_run.py`）を取り、取れなければ「別の窓で実行中」と返して何もしない。プロセスが死ねば OS が解放するので、キャンセルや強制終了でもロックは残らない。範囲は同じ PC の同じ Windows ユーザーだけ

### エラー

- GPU（CUDA）が使えないときは CPU で動かさない。**エラーを出して終える**。結果ダイアログに、見つかった
  onnxruntime の provider と必要な CUDA / cuDNN の版を出す
- アイテム単位のエラー（プレビュー取得や更新の失敗）では止めず、数えて最後にまとめて報告する

## 2. 前提となる MEGA 側の制約（SDK v10.17.0 で確認）

| 制約 | 値 | 出典 |
| --- | --- | --- |
| 1 ノードあたりのタグ数 | **最大 10**（超えると `API_ETOOMANY`） | `MegaClient::MAX_NUMBER_TAGS` |
| タグ全体の長さ | `,` 区切りで連結して **3000 バイト以内** | `MegaClient::MAX_TAGS_SIZE` |
| 使えない文字 | `,`（区切り文字） | `megaapi.h` `addNodeTag` |
| 重複判定（add / remove） | 大文字小文字を無視、**アクセントは区別** | `addTagToNode` / `removeTagFromNode` が `getTagPosition(..., stripAccents=false)` |
| description の長さ | 3000 バイト以内 | `MAX_NODE_DESCRIPTION_SIZE` |

**10 個という上限は、ユーザーが手で付けたタグと共有になる。**WD のモデルは閾値 0.30 で平均 47 個の
general タグを出すので（§4）、推論結果をタグ 1 個ずつに分けて付けることはできない。§1 で 1 タグに
まとめることにしたのはこのため。

**タグ検索（`MegaSearchFilter::byTag`）は部分一致。**検索語の前後に `*` を付けたパターン（`TextPattern`）を、
タグ 1 個ずつと照合する（`NodeSearchFilter::isValidTagSequence`）。大文字小文字とアクセントは区別しない。
sqlite 経由の検索も同じ関数を呼ぶ。1 回の検索で指定できるタグ語は 1 つだけで、`,` を含めると結果は空になる。
`byDescription` も部分一致。したがってタグを分けても、`hair` で検索すれば `long_hair` に当たる。
1 タグにまとめて失うのは「`hair smile` のように 2 語にまたがる検索も当たってしまう」程度。

## 3. 処理の流れ

```
command "tag-item" / "tag-folder":
    targets = 選択アイテム                       # tag-folder なら items.descendants で配下のファイルを全部
    targets = [t for t in targets if 拡張子が画像/動画]
    model = load_model()                          # CUDA が使えなければエラーで終了
    progress(0, len(targets))
    for item in targets:
        check_cancelled()
        if item に wd: タグがある: skipped += 1; continue     # タグはコンテキスト / items.descendants の Item に入っている
        try:
            jpg = fetch_preview(item)
        except NoPreview: skipped += 1; continue
        scores = model.predict(jpg); delete jpg
        tags = select_tags(scores)                # 閾値、wd: 2000 バイト、全体 3000 バイト
        update(item, tags_add=tags)
        progress(i, len(targets))
    return "Tagged N, skipped M, failed K"
```

## 4. 決定の根拠: タグの長さの実測

モデル（wd-eva02-large-tagger-v3）の `selected_tags.csv` に載っている 10,861 タグの長さ（UTF-8 バイト）:

| カテゴリ | 平均 | 中央値 | 上位10% | 最大 | 出現頻度で重み付けした平均 |
| --- | --- | --- | --- | --- | --- |
| general | 11.8 | 11 | 18 | 44 | 9.5 |
| character | 17.3 | 16 | 26 | 66 | 16.4 |
| rating | 9.0 | — | — | 12 | — |

推論でよく出るのは出現頻度の高いタグで、区切り 1 文字を含めると 1 タグ 10〜13 バイトになる。
3000 バイトを丸ごと使えば 230〜270 個、2000 バイトでも約 150 個入る。

旧ツールの DB に保存してある 528,581 件の推論結果（同じモデル、閾値 0.30 / 0.50 / 0.40）を、
§1 の書式に当てはめて計算した結果:

| 項目 | 平均 | 中央値 | 上位10% | 上位1% | 最大 |
| --- | --- | --- | --- | --- | --- |
| general の個数 | 46.9 | 45 | 66 | 93 | 595 |
| character の個数 | 0.7 | 1 | 2 | 4 | 73 |
| `wd:` タグのバイト数 | 512 | 494 | 727 | 1,039 | 6,909 |
| プラグインのタグ合計のバイト数（`,` 区切り） | 549 | 532 | 771 | 1,085 | 7,031 |

`wd:` タグが 2000 バイトを超えたのは 48 件（0.01%）、合計が 3000 バイトを超えたのは 4 件だけだった。
最大値のような外れ値（ノイズのような画像と思われる）を除けば、**バイト数は事実上の制約にならない**。
character が 4 個以上の画像は 6,152 件（1.2%）。キャラは 1 タグにまとめるので人数の上限は設けない
（キャラ名は平均 17 バイトなので、外れ値の 73 人でも 1,700 バイト程度）。

## 5. 未決事項

大きいフォルダの扱いは §1「大きいフォルダと MEGA への負荷」で決定。そのうえで、実際の利用で分かったことと追うこと:

- **実利用での件数（2026-10-02、ユーザーによる通常利用。負荷テストではない）。**本番アカウント（Pro I）で、
  2000 件を超えるフォルダを含め合計およそ 8000 件を処理し、API 制限によるエラーは出ずに最後まで通った。
  大量件数への懸念は少し下がったが、**確定ではない**: アカウントの種類（Pro I）に依存しうること、
  MEGA 側が今後何らかの対応をとる可能性があること
- **そのときの処理速度は 1 件およそ 0.8 秒**（ほとんどが MEGA との通信待ち）。1 件ずつ順番に処理する作り（§1）なので、この待ち時間が実質的なインターバルとして働き、制限にかからなかった可能性がある。回線や処理が速い環境、あるいは先読み・並列化を入れた場合は同じ結果になるとは限らない
- **転送量の上限（追跡中）。**その時点でアカウントの「転送」の使用量は 16.5 GB。プレビューの取得
  （`items.fetchPreview`）が転送量に数えられているなら、上限に達した時点で取得が止まる可能性がある。
  ユーザーが使用量の推移を見て確かめる。止まる場合の出方（どのエラーが返るか、結果ダイアログでどう見えるか）
  もそのとき確認する


## 6. プラグイン基盤（MegaExplorer 側）への宿題

このプラグインを作るのに今の基盤で足りないもの。直すのは本体リポジトリの `feature/plugin-v1` で行う。

| # | 内容 | 必須度 | 現状 |
| --- | --- | --- | --- |
| 6-1 | **ファイルとフォルダでメニューを出し分ける**（設計書 `docs/investigations/STUDY_PLUGIN_V1_DESIGN.md` §3・§4 の `when`） | 済（本体 `feature/plugin-v1`） | `targets`（`files`/`folders`/`any`）と `extensions` を実装。合わない項目は灰色。`sites`・`minCount`・`maxCount` は未実装 |
| 6-2 | フォルダ配下の再帰列挙（`items.descendants`） | 済（本体 `feature/plugin-v1`） | 深さ優先の前順、最初の呼び出しで一覧（ハンドル）を確定し、各ページを返す時点で消えていたものは飛ばす。カーソルは `"<一覧番号>:<位置>"` で、一覧は実行が終わると捨てる。`_taggable_files_under` は `ctx.descendants(folder, type="file")` を回すだけになった |
| 6-3 | Item に種別（`kind`）を載せる | 任意（今は拡張子で判定する） | なし |
| 6-4 | 結果の詳細表示。スキップ・失敗の一覧、GPU が使えないときのエラーをここに出す | 済（本体 `feature/plugin-v1`） | 設計書 §6-6 の `details` とトーストの［詳細］は**採らなかった**（トーストは 6 秒で消え、長い処理の結果を見逃す）。代わりにコマンドごとに manifest で `"result": "toast"`（既定）/ `"dialog"` を選ぶ。dialog なら進捗ダイアログがそのまま結果表示に変わり（進捗なしなら終了時に開く）、Close まで残る。結果は `message` 1 つ（複数行可）。エラーは JSON-RPC の決まりで `error.message` を 1 文にし、全文を `error.data.message` に入れる。トーストは 3 行で切り、全文はログへ |
| 6-5 | タグ更新の仕様: 一致判定を SDK に合わせる＋ `add` と `remove` の重複を許す | 済（本体 `feature/plugin-v1`） | 結果は「今のタグ − `remove` ＋ `add`」で、両方にあるタグは残る。アプリが差分だけを SDK に送る（消す → 付ける）。一致判定は SDK の add/remove と同じく大文字小文字だけ無視し、アクセントは区別する（§2。アクセントも無視するのは検索だけだった）。remove はアイテムに付いている表記で送る。プラグインの `tags.tag_changes` は削除 |
| 6-6 | 10 個の上限に当たったときのエラーを、-32010 以外の分かる形で返すか | 要確認 | `API_ETOOMANY` は今 -32010（MegaError）として返る |
| 6-7 | items.update でタグの remove を add より先に実行する | 済（本体 `feature/plugin-v1`） | retag で 10 枠・3000 バイトが埋まっていても付け替えられる |
| 6-8 | アプリの検索でタグを探せるようにする | 済（本体 `feature/plugin-v1`） | 検索ボックスに `tag:語` と書くとタグ検索（`tag:"空白入り"` も可）。複数書くと AND、部分一致。`tag:chara:hatsune_miku` のようにプレフィックスごと書けば種類で絞れる。何も付けない語は今までどおり名前検索 |
| 6-9 | **初回の環境構築が起動待ちのタイムアウトに入る**: 新しい PC で初めて動かすと、`uv run` が Python を起動する前に venv を作り、依存パッケージ（onnxruntime-gpu など数百 MB）を取得する。その間ダイアログは「Preparing…」のままで、プラグインからは進捗を送れず、しかもこの時間が `initialize` の 5 分のタイムアウトに含まれる。案: (a) 配布手順に「最初に `uv sync`」と書く、(b) タイムアウトを延ばす、(c) manifest に一度だけ動かす `setup` コマンドを書けるようにし、アプリがその間は別の表示をする | 配布するまでに | 開発機は `uv sync` 済みなので起きない |
| 6-10 | 進捗の件数に単位（MB など）を付けられるようにする | 後回し | `current / total` を数字のまま出す。プラグイン側で MB に換算して回避している |
| 6-11 | プロパティ画面のタグ表示 | 済（本体 `feature/plugin-v1`） | 1 行ずつ省略、クリックで全文。ダイアログはスクロールしないので、2000 バイト近い `wd:` タグを開くと小さいウィンドウでははみ出す（ScrollView で包むと中の行にクリックが届かなかった） |
| 6-12 | コンテキストの `items` を `Item` 形式にする（タグ・説明・サイズなど入り） | 済（本体 `feature/plugin-v1`） | `items.get` と同じ形（同じ関数で作る）。ヘルパーの `ctx.items` もそのまま使え、選択ファイルを `items.get` で取り直す処理は削除した |
| 6-13 | 確認ダイアログ（設計書 §6-3 の `ui.confirm`） | 済（本体 `feature/plugin-v1`） | モーダル。`title` 省略でプラグイン名、`okLabel` 省略で OK。`danger` で OK ボタンを赤字にし、初期フォーカスをキャンセルに置く。Esc とキャンセルは `{ok: false}`。答える前にプラグインが終わればダイアログも閉じる。複数のプラグインが同時に聞いたら古い順に 1 つずつ出す。ヘルパーは `ctx.confirm()` |

### 6-A. 次に対応する改善（2026-10-02 決定）

WD Tagger を一通り作ってみて、どのプラグインでも効く書きにくさとして選んだもの。直すのは本体
`feature/plugin-v1`。終わったら、このプラグインを新しい API に書き直して確かめる。

| 順 | 項目 | 決めたこと |
| --- | --- | --- |
| 1 | 6-5 タグ更新（**済**） | `tags: {add, remove}` を「`remove` を消してから `add` を付けた状態にする」と定義し直す。両方に同じタグがあればそのタグは残す（エラーにしない）。アプリが現在のタグとの差分を取り、実際に変わるものだけ SDK に送る（消す → 付ける）。一致判定は SDK と同じ（実装時に SDK を確かめたら、add/remove は大文字小文字だけ無視でアクセントは区別だったので、そちらに合わせた）。`tags.set`（最終形を丸ごと渡す）は、ユーザーのタグを入れ忘れると消してしまうので採らない。retag は「古いプラグインのタグを全部 remove、新しいタグを全部 add」と書くだけになり、`tag_changes` は不要になる |
| 2 | 6-12 コンテキストの `items`（**済**） | `items.get` と同じ `Item` 形式にする。**設計書 §6-2 の「コンテキストは ID と名前だけ」からの変更**。アプリ側はメモリ上の読み取りなので数千件でも重くない。値がクリック時点のものなのは今と同じ |
| 3 | 6-2 `items.descendants`（**済**） | 設計書 §6-3・§6-5 どおり: `{handle, type?, cursor?, limit?}` → `{items, nextCursor}`、深さ優先の前順、最初の呼び出しで一覧を確定。ヘルパーに `ctx.descendants()` を足す |
| 4 | 6-13 `ui.confirm`（**済**） | 設計書 §6-3 どおり: `{title?, message, okLabel?, danger?}` → `{ok}`。ユーザーが答えるまで応答しない。Retag（特にフォルダ）で使う |
| 5 | 6-4 結果の表示（**済**、決めたことは §6 の表へ） | 当初は設計書 §6-6 の `details` の予定だったが、相談して `"result": "dialog"` に変えた |

順番は、通信の仕様だけで済む小さいもの（1〜3）を先に、画面を作るもの（4・5）を後にした。
